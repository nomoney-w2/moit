- Q: 리스트뷰 카드 컴포넌트의 입력 데이터 인터페이스를 어떻게 설계할까요? → A: 별도 ViewModel 변환 (Recommended). 외부 입력은 사용자 제시 샘플(`Meeting + Participant[]`) 형태로 받되, 카드 컴포넌트는 내부적으로 `RankedSlot[]` ViewModel을 소비. mock ↔ 실 API 어느 쪽이 들어와도 어댑터 한 곳만 교체.
- Q: 0표 슬롯(가능 인원 0명)을 리스트뷰에 어떻게 처리할까요? → A: 리스트 하단에 노출(현재 안 유지). 뱃지는 부여되지 않으며 6위 이하 카드처럼 표시.
- Q: 카드의 초기 펼침 상태는 어떻게 할까요? → A: 전체 접힘. 사용자가 관심 있는 슬롯만 탭하여 펼침 (정보 과밀 방지).
- Q: 동률 슬롯들 사이의 보조 정렬 기준은? → A: 임박한 날짜 우선. 같은 인원 수 그룹 내에서는 가까운 미래 날짜 → 같은 날짜 내에서는 이른 시간 순.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 후보 일정 순위 뱃지를 한눈에 확인 (Priority: P1)

참여자가 투표 결과 화면(리스트뷰)에 진입했을 때, 각 후보 시간 슬롯이 "가능한 인원 수"가 많은 순으로 정렬된 카드 리스트를 보고, 1위부터 5위까지의 카드에는 색상이 다른 순위 뱃지가 표시되어 있어 어떤 일정이 가장 유력한지 즉시 인지할 수 있다.

**Why this priority**: 서비스의 핵심 가치(빠른 일정 정렬)를 시각적으로 가장 잘 전달하는 요소. 이 한 가지만 있어도 "결과 보기" 사용자 가치를 단독으로 제공할 수 있어 MVP의 기반이 된다.

**Independent Test**: test 페이지를 열어 9명이 투표한 mock 데이터(여러 후보 슬롯 포함)를 입력했을 때, 가능한 인원 수 내림차순으로 카드가 정렬되고 상위 5개 카드에 1~5위 뱃지가 적절히 부여되는지 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 6개 이상의 후보 시간 슬롯이 있고 인원 수가 모두 다른 mock 데이터, **When** 사용자가 리스트뷰에 진입, **Then** 카드는 인원 수 내림차순으로 정렬되고 상위 5장에만 순위 뱃지가 표시되며 6위 이하 카드에는 뱃지가 없다.
2. **Given** 2명이 공동 2위인 후보 슬롯이 있는 데이터, **When** 사용자가 리스트뷰를 확인, **Then** 두 카드 모두 "2위" 뱃지를 가지고 그다음 카드는 "4위" 뱃지를 갖는다(3위 스킵).
3. **Given** 뱃지 색상 규칙(1위 단독 색, 2~3위 동일 색, 4~5위 동일 색), **When** 카드가 렌더링, **Then** 동일 그룹의 뱃지는 동일 색을 사용하고 1위 뱃지는 가장 강조된 색을 사용한다.

---

### User Story 2 - 카드 펼쳐 참여자 목록 확인 (Priority: P1)

참여자가 특정 후보 시간 슬롯의 카드를 탭하면 카드가 아코디언처럼 펼쳐져 "가능한 사람" 목록과 "못 오는 사람" 목록을 확인할 수 있다. 다시 탭하면 접힌다.

**Why this priority**: 어떤 사람이 가능한지 확인하는 건 일정 결정의 핵심 정보. 리스트뷰가 단순 정렬로 끝나면 가치가 절반 이하로 떨어진다.

**Independent Test**: 카드 헤더 영역을 클릭했을 때 본문이 펼쳐지고 가능/불가 참여자 이름이 노출되는지, 다시 클릭하면 접히는지 확인.

**Acceptance Scenarios**:

1. **Given** 접혀 있는 카드, **When** 사용자가 카드 헤더를 탭, **Then** 카드 본문이 펼쳐지며 "N명이 가능해요" / 가능 참여자 이름 / "M명이 못와요" / 불가 참여자 이름이 순서대로 노출된다.
2. **Given** 펼쳐진 카드, **When** 사용자가 동일 카드 헤더를 다시 탭, **Then** 카드가 접힌다.
3. **Given** 여러 카드가 동시에 펼쳐진 상태, **When** 추가로 다른 카드를 탭, **Then** 각 카드는 독립적으로 토글되어 다중 펼침이 허용된다.

---

### User Story 3 - 예외 상태 안내 (Priority: P2)

투표자가 0명이거나 모든 셀이 동률이거나 후보 슬롯이 5개 이하인 경계 케이스에서, 사용자가 혼란 없이 적절한 안내/표현을 받는다.

**Why this priority**: 핵심 흐름은 아니지만, 빈 상태/엣지케이스 누락은 신뢰도를 크게 떨어뜨림. P1 이후 반드시 보강해야 한다.

**Independent Test**: 빈 mock / 전원 동률 mock / 5슬롯 이하 mock을 각각 주입하여 요구된 안내가 노출되는지 확인.

**Acceptance Scenarios**:

1. **Given** 투표자 0명 mock, **When** 리스트뷰 진입, **Then** 카드 대신 빈 상태 안내 문구만 노출된다(뱃지 없음).
2. **Given** 모든 셀이 동일 득표(전원 동률) mock, **When** 리스트뷰 진입, **Then** 모든 카드가 공동 1위로 처리되되 임박한 날짜 순으로 최대 5장까지만 노출된다.
3. **Given** 후보 슬롯이 총 5개 이하인 mock, **When** 리스트뷰 진입, **Then** 모든 카드에 1~5위 뱃지가 부여된다(스펙상 제한 없음).

---

### Edge Cases

- 동률 처리: 2명 공동 2위 → 다음은 4위(3위 스킵). 그룹 색상 규칙(2~3위 동일 색, 4~5위 동일 색)은 "표시되는 순위 숫자" 기준으로 적용한다.
- 0표 슬롯: 가능 인원이 0인 슬롯은 순위 산정에서 제외하며 뱃지를 부여하지 않는다(다만 슬롯 자체는 리스트에 포함되며 6위 이하 형태로 표시).
- 부분 투표(`hasVoted=false` 참여자 존재): 미투표자는 가능/불가 어디에도 카운트되지 않고 표시되지 않는다.
- 전원 동률 + 5장 초과: 임박한 날짜 순(오름차순)으로 잘라 5장만 노출하고 나머지는 숨긴다.
- 카드 펼침 상태 유지: 페이지 내 다른 인터랙션(예: 다른 카드 펼침) 시 기존에 펼쳐진 카드 상태는 그대로 유지된다.
- 한 후보 시간 슬롯의 가능 인원이 매우 많을 때: 펼친 본문의 이름 목록이 카드 영역을 자연스럽게 늘리며 잘리지 않는다.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 시스템은 후보 시간 슬롯 목록을 "가능한 인원 수" 내림차순으로 정렬해 카드 리스트로 표시해야 한다.
- **FR-002**: 시스템은 정렬된 카드 중 1위부터 5위까지에만 순위 뱃지를 부여하고, 6위 이하 카드에는 뱃지를 부여하지 않아야 한다.
- **FR-003**: 시스템은 동일 인원 수 슬롯에 동일 순위를 부여하고, 다음 순위는 인원 수 그룹 크기만큼 건너뛰어야 한다(예: 공동 2위 2개 → 다음 4위).
- **FR-004**: 시스템은 뱃지 색상을 그룹 규칙에 따라 적용해야 한다 — 1위는 단독 강조 색, 2~3위는 동일 색, 4~5위는 동일 색.
- **FR-005**: 사용자는 카드 헤더를 탭하여 카드 본문을 펼치고 접을 수 있어야 한다(아코디언).
- **FR-006**: 펼쳐진 카드 본문은 "N명이 가능해요" 헤더, 가능 참여자 이름 목록, "M명이 못와요" 헤더, 불가 참여자 이름 목록을 순서대로 표시해야 한다.
- **FR-007**: 카드 헤더는 날짜(요일 포함), 시간 범위, 순위 뱃지(1~5위인 경우), 가능 인원 수 요약을 표시해야 한다.
- **FR-008**: 시스템은 0표 슬롯을 순위 산정 대상에서 제외하되 카드 자체는 리스트 하단에 노출해야 한다.
- **FR-009**: 시스템은 투표자가 0명일 때 카드 대신 빈 상태 안내 문구를 표시해야 한다.
- **FR-010**: 시스템은 모든 카드가 동률(전원 동률)일 때 전 카드를 공동 1위로 처리하고 임박한 날짜 순으로 최대 5장만 노출해야 한다.
- **FR-011**: 시스템은 카드 다중 펼침을 지원하며, 페이지 진입 시 모든 카드는 접힘(collapsed) 상태가 기본이다.
- **FR-012**: 리스트뷰는 test 페이지(`/test/...`)에서 mock 데이터로 단독 동작 가능해야 한다. 카드 컴포넌트의 직접 입력은 표시용 ViewModel(`RankedSlot[]` 등)이며, 사용자 제공 샘플 데이터 → ViewModel 변환은 별도 어댑터 함수로 분리한다(mock과 실 API가 한 어댑터를 통해 교체 가능).
- **FR-013**: 페이지 헤더는 모임 제목과 "N명이 투표했어요" 요약을 표시해야 한다.
- **FR-014**: 페이지 하단에는 "투표하기" / "투표 수정하기" CTA 영역(스펙상 placeholder)이 위치한다(이번 범위에서는 시각적 영역만 확보, 동작은 후속).
- **FR-015**: 동률 슬롯 그룹 내 보조 정렬은 "임박한 미래 날짜 우선 → 같은 날짜 내 이른 시간 우선" 순으로 적용한다.

### Key Entities _(include if feature involves data)_

- **Meeting (모임)**: 투표 대상 모임. 속성: `id`, `title`, `dates`(후보 날짜 배열), `status`, `finalizedDate`, `maxParticipantCount`, `hostName`, `timeRange`(시작/종료/슬롯 수).
- **Participant (참여자)**: 모임 참여자. 속성: `id`, `name`, `voteDates`(투표한 날짜), `voteTimeSlots`(날짜별 시간 슬롯 가능 여부 2D), `hasVoted`.
- **TimeSlot (시간 슬롯)**: 후보 일정의 최소 단위. 날짜 + 시간 범위로 식별되며, 해당 슬롯에 가능한 참여자 / 불가 참여자 / 가능 인원 수를 파생 속성으로 갖는다.
- **RankedSlot (순위 부여된 시간 슬롯)**: TimeSlot에 순위(1~5 또는 null)와 색상 그룹(rank1 / rank2-3 / rank4-5 / none)이 결합된 표시용 모델.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 처음 리스트뷰에 진입한 사용자가 "가장 유력한 일정"(1위)을 5초 이내에 식별할 수 있다.
- **SC-002**: 사용자의 90% 이상이 안내 없이 카드를 탭하여 가능/불가 참여자 목록을 펼칠 수 있다(아코디언 어포던스 명확성).
- **SC-003**: 후보 슬롯이 30개인 mock 데이터에서도 카드 리스트가 1초 이내에 화면에 그려진다.
- **SC-004**: 동률·빈 상태·5장 이하 등 정의된 모든 예외 케이스에서 mock 시나리오 기준 100% 의도된 화면이 노출된다.
- **SC-005**: 본 기능을 실데이터에 연결할 때 컴포넌트의 입력 인터페이스(props/데이터) 변경 없이 mock → API 응답 매핑 한 곳만 교체하면 동작한다.

## Assumptions

- 데이터 형태는 사용자가 제시한 샘플(`{ id, title, dates, status, finalizedDate, maxParticipantCount, participants[{id,name,voteDates,voteTimeSlots,hasVoted}], hostName, timeRange }`)을 외부 입력 가정으로 하며, 카드 컴포넌트는 이를 변환한 ViewModel(`RankedSlot[]`)을 소비한다. 현재 프로덕션 DTO(`MeetResponse`)에는 `voteTimeSlots`/`timeRange`가 없으므로 mock 어댑터에서만 사용하며, 추후 백엔드 확장 시 동일 어댑터 인터페이스로 교체.
- "후보 시간 슬롯"은 `dates × timeRange.slotCount`의 격자에서 한 칸을 의미한다. 가능/불가 판단은 `participants[i].voteTimeSlots[dateIndex][slotIndex]`를 사용한다.
- 임박한 날짜 정렬은 "오늘로부터 가까운 미래 날짜 우선"으로 가정한다.
- 페이지 라우트는 기존 test 디렉터리 컨벤션을 따라 `/test/<slug>`에 배치한다. 정확한 슬러그는 plan 단계에서 결정.
- 뱃지 색상 토큰은 디자인 시스템에서 매핑 가능한 가장 가까운 색을 사용하되, 정확한 헥스코드는 Figma 노드(3650-30335 / 3627-6468)에서 추후 추출.
- "투표하기 / 투표 수정하기" CTA의 동작 로직은 본 기능 범위 밖이며 빈 셸만 둔다.

## Out of Scope

- 테이블뷰(히트맵) 셀에서의 1위 강조 표현(향후 별도 작업).
- 셀 상세 모달의 헤더 순위 뱃지 노출(향후 별도 작업; 본 기능에서는 리스트뷰 카드 한정).
- 실제 API 연동 및 상태 관리(react-query/store) 통합.
- "투표하기 / 투표 수정하기" CTA의 라우팅·트래킹 로직.
- 접근성(키보드 포커스, ARIA) 고도화 — 기본 수준만 제공하고 후속에서 보강.
