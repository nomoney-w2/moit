# Feature Specification: 모임 테이블뷰 화면

**Feature Branch**: `feat/#133-meet-table-view`
**Created**: 2026-04-30
**Status**: Draft
**Input**: 모임 결과 화면(/meet/{meetingId})에 30분 단위 시간 슬롯 기반 투표 히트맵 테이블뷰를 기본 진입 화면으로 추가하고, 우상단 토글로 기존 캘린더뷰(VoteResultDataView)와 전환할 수 있도록 한다.

## Clarifications

### Session 2026-04-30

- Q: 투표 단위는 어떻게 할까? → A: 30분 시간 슬롯으로 확장 (데이터 모델/API/투표 화면 확장은 별도 명세, 이 명세는 그 위의 표시 계층)
- Q: 기존 /meet/{meetingId} 결과 화면과의 관계 → A: 테이블뷰가 기본 진입, 우상단 토글로 기존 캘린더뷰(VoteResultDataView)로 전환
- Q: 셀 색상 농도 의미 → A: 가능 인원수 기준 상위 5개 슬롯에 1위 100%, 2위 70%, 3위 50%, 4위 30%, 5위 10% 농도. 그 외 슬롯은 베이스 톤
- Q: 하단 버튼 표시 로직 → A: '투표 수정하기' + '투표하기' 둘 다 항상 표시 (현재 VoteActionButtons와 동일)
- Q: 좌상단 '캘린더+' 아이콘 동작 → A: 새 모임 생성으로 이동 (기존 동작 유지)
- Q: 가로 스크롤 방식 → A: 가로 + 세로 둘 다 스크롤 (페이지네이션 X)
- Q: 셀 탭 인터랙션 → A: 이번 명세에서는 정의하지 않음 (추후 결정)
- Q: 토글로 전환되는 캘린더뷰 데이터 표현 → A: 기존 VoteResultDataView 그대로 재사용 (시간 슬롯 데이터의 캘린더뷰 매핑은 별도 결정)

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 시간 슬롯 히트맵으로 가능한 시간대 한눈에 파악 (Priority: P1)

모임 참여자(또는 호스트)가 `/meet/{meetingId}` 진입 시, 후보 날짜를 가로축으로, 9시~21시 시간대를 세로축으로 하는 30분 단위 격자에서 가능 인원수가 많은 시간 슬롯이 진한 파란색으로, 적은 슬롯은 베이스 톤으로 표시된 히트맵을 본다. 색의 진하기를 통해 어느 날·어느 시간대가 모이기 가장 좋은지 즉시 파악할 수 있다.

**Why this priority**: 이 기능의 핵심 가치 — "투표 결과를 빠르게 분류해 가장 가능성 높은 시간대를 보여준다"는 서비스 핵심 가치 제안과 직결된다. 이 기능 없이는 화면의 존재 이유가 없다.

**Independent Test**: 임의의 시간 슬롯 투표 데이터(예: 9명 참여자, 후보 날짜 7개, 슬롯별 가능 인원수 다양)로 진입 시, 가능 인원수 1위 슬롯이 가장 진하게, 5위 슬롯이 가장 연하게, 6위 이하는 베이스 톤으로 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 9명이 투표한 모임, **When** `/meet/{meetingId}` 진입, **Then** 상단에 "9명이 투표했어요"가 표시되고, 시간 슬롯 격자가 가능 인원수 기준 상위 5개에 차등 농도(100/70/50/30/10%)로 채워진다
2. **Given** 가능 인원수 1위 슬롯이 7명, 2위 5명, 3위 4명, 4위 2명, 5위 1명, 6위 이하 0명, **When** 화면 진입, **Then** 1위 셀은 가장 진한 파랑, 2~5위 셀은 단계별로 옅어지고, 6위 이하·미투표 셀은 베이스 톤
3. **Given** 가능 인원수 동률인 슬롯이 여러 개, **When** 동률 슬롯이 상위 5위 컷오프에 걸침, **Then** 동률 슬롯들은 모두 같은 농도로 표시(컷오프에서 잘라내지 않고 동률은 함께 묶음)
4. **Given** 아무도 투표하지 않은 모임, **When** 화면 진입, **Then** 상단에 "0명이 투표했어요"가 표시되고 모든 셀은 베이스 톤(채색 없음)

### User Story 2 - 가로·세로 스크롤로 많은 후보 날짜와 긴 시간 범위 탐색 (Priority: P1)

후보 날짜가 4개를 넘거나 화면에 한눈에 들어오지 않을 때, 사용자는 그리드를 좌우로 스크롤해 다른 날짜를 보고, 위아래로 스크롤해 9시~21시 범위 내 다른 시간대를 본다. 헤더(날짜 라벨)와 시간 컬럼은 스크롤 시에도 적절히 따라와 맥락을 유지한다.

**Why this priority**: 후보 날짜는 모임마다 1~수십 개로 가변적이다. 화면 폭에 들어오지 않는 후보 날짜를 볼 수 없다면 결과 화면으로서 기능하지 못한다.

**Independent Test**: 후보 날짜 7개 모임 진입 → 좌우 스와이프로 모든 날짜를 확인할 수 있는지, 시간 영역도 위아래 스크롤로 모든 시간대를 확인할 수 있는지 확인.

**Acceptance Scenarios**:

1. **Given** 후보 날짜 7개의 모임, **When** 화면 진입, **Then** 처음에는 첫 4일가량이 보이고 우측 가장자리에 다음 컬럼이 일부 잘려 보여 더 있음을 암시한다
2. **Given** 그리드가 표시된 상태, **When** 좌→우 스와이프(또는 마우스 가로 스크롤), **Then** 다음 날짜 컬럼들이 부드럽게 이동해 표시된다
3. **Given** 그리드가 표시된 상태, **When** 위→아래 스크롤, **Then** 시간대(예: 13시 이후)가 표시된다
4. **Given** 가로·세로 동시 스크롤 가능 영역, **When** 사용자가 스크롤, **Then** 좌측 시간 컬럼은 가로 스크롤에 영향을 받지 않고 고정되고, 상단 날짜 헤더는 세로 스크롤에 영향을 받지 않고 고정된다

### User Story 3 - 토글로 기존 캘린더뷰 전환 (Priority: P2)

사용자가 우상단 토글 스위치를 누르면, 동일한 투표 데이터를 기존 캘린더뷰(VoteResultDataView; 날짜별 가능/불가 인원 카드 형식)로 전환해 본다. 다시 누르면 테이블뷰로 돌아온다.

**Why this priority**: 시간 슬롯 그리드는 정보 밀도가 높지만 "누가 가능한가"의 인지가 어렵다. 기존 캘린더뷰는 사용자에게 익숙한 형태로 같은 데이터를 다른 관점에서 보여준다. 핵심 가치는 P1 히트맵에서 이미 달성되므로 P2.

**Independent Test**: 테이블뷰에서 토글 스위치 클릭 시 VoteResultDataView 화면으로 즉시 전환되고, 다시 클릭 시 테이블뷰로 돌아오는지 확인.

**Acceptance Scenarios**:

1. **Given** 기본 진입 상태(테이블뷰 활성), **When** 우상단 토글을 누름, **Then** 화면이 기존 캘린더뷰(VoteResultDataView)로 전환되고 토글 시각 상태가 캘린더뷰 활성으로 바뀐다
2. **Given** 캘린더뷰가 활성, **When** 토글을 다시 누름, **Then** 테이블뷰로 복귀
3. **Given** 토글로 캘린더뷰 전환, **When** 사용자가 페이지를 떠났다 다시 진입, **Then** 다시 기본인 테이블뷰로 시작 (전환 상태 유지 여부는 Assumption 항목 참조)

---

### User Story 4 - 모임 헤더에서 모임 정보·공유·새 모임 생성 (Priority: P2)

화면 상단에서 사용자는 (a) "{호스트명}님이 초대한 {모임명}" 타이틀로 어떤 모임인지 확인하고, (b) 우상단 공유 아이콘으로 링크를 공유하고, (c) 좌상단 '캘린더+' 아이콘으로 새 모임 생성 플로우로 진입할 수 있다.

**Why this priority**: 표시 정보의 맥락(어느 모임인지)과 진입점(공유, 새 모임)이 없으면 결과 화면이 분리된 페이지로 동작하지 못한다. 단, 결과 표시 자체가 P1이므로 부속 진입점은 P2.

**Independent Test**: 헤더의 세 요소가 각각 올바른 데이터/동작과 연결되는지 개별 확인 — 타이틀이 모임명/호스트명 반영, 공유 버튼이 기존 공유 동작 트리거, 캘린더+ 버튼이 새 모임 생성 진입.

**Acceptance Scenarios**:

1. **Given** "두쫀쿠 투어"라는 모임에 호스트 "김야뿌"가 만든 상태, **When** 화면 진입, **Then** 헤더 중앙에 "김야뿌님이 초대한 두쫀쿠 투어"가 표시
2. **Given** 화면 진입, **When** 우상단 공유 아이콘 탭, **Then** 기존 공유 동작(시스템 공유 시트 또는 링크 복사)이 트리거된다
3. **Given** 화면 진입, **When** 좌상단 캘린더+ 아이콘 탭, **Then** 새 모임 생성 플로우(현재의 새 모임 생성 진입점)로 이동한다

---

### User Story 5 - 하단 투표하기·투표 수정하기 액션 (Priority: P2)

화면 하단에 항상 표시되는 두 버튼을 통해 사용자는 새로 투표하거나(투표하기) 기존 투표를 수정한다(투표 수정하기). 두 버튼은 본인 투표 상태와 무관하게 항상 노출된다(현재 동작 유지).

**Why this priority**: 결과를 보고 행동(투표/수정)으로 연결되는 핵심 진입점. P1 표시 자체가 더 우선이지만 이 액션이 빠지면 결과만 보고 끝나는 dead-end 화면이 된다.

**Independent Test**: 화면 진입 시 두 버튼이 동시에 표시되고 각각 `/meet/{id}/register`, `/meet/{id}/edit` 진입점으로 동작하는지 확인.

**Acceptance Scenarios**:

1. **Given** 결과 테이블뷰 진입, **When** 화면 하단을 봄, **Then** "투표 수정하기"(보조 스타일)와 "투표하기"(주 스타일) 두 버튼이 가로로 나란히 표시
2. **Given** 두 버튼이 표시, **When** "투표하기" 탭, **Then** 투표 등록 진입점으로 이동
3. **Given** 두 버튼이 표시, **When** "투표 수정하기" 탭, **Then** 투표 수정 진입점으로 이동
4. **Given** 가로·세로 스크롤 중, **When** 그리드를 위아래로 스크롤, **Then** 하단 버튼 영역은 화면 하단에 고정되어 사라지지 않는다

---

### Edge Cases

- **투표자 0명**: 모든 셀이 베이스 톤. 상단 카운트는 "0명이 투표했어요". 하단 버튼은 그대로 표시.
- **모든 슬롯에 동일 인원수가 투표한 경우**(예: 모두 1명): 모든 슬롯이 동률 1위가 되어 같은 농도(100%)로 표시. (동률 정책은 FR-006 참조)
- **상위 1위가 모두 0명일 때**(아무도 어느 슬롯도 가능하지 않음): 0명도 "1위"로 분류해 100% 농도로 칠하지 않음. **0명 슬롯은 농도 부여 대상에서 제외**한다 → 베이스 톤.
- **상위 5위 컷오프에 동률**: 5위가 3개 동률이면 모두 10% 농도로 함께 표시(잘라내지 않음). 6개 이상 동률이어서 5위가 비대해지면? → 모두 같은 5위 농도로 표시.
- **후보 날짜가 1개 또는 2개**: 가로 스크롤 불필요, 화면 폭에 균등 분배.
- **시간 범위가 후보 날짜별로 다름**: 모든 날짜 컬럼은 동일 시간 범위(9~21시)로 표시. 해당 날짜에 투표 가능 시간이 없는 슬롯은 베이스 톤.
- **토글 상태와 라우팅**: 페이지 새로고침/재진입 시 기본은 테이블뷰. (URL 쿼리/세션 보존 여부는 Assumption 참조)
- **데이터 로딩 중**: 그리드 영역에 스켈레톤 또는 로딩 표시. 헤더(타이틀)는 가능하면 캐시된 모임 메타로 즉시 표시.
- **모임 데이터 조회 실패**: 기존 메타데이터 폴백 패턴(현 page.tsx의 try/catch와 동일)으로 처리.

## Requirements _(mandatory)_

### Functional Requirements

#### 그리드 표시

- **FR-001**: 시스템은 `/meet/{meetingId}` 진입 시 기본으로 시간 슬롯 테이블뷰를 표시해야 한다
- **FR-002**: 그리드의 가로축(컬럼)은 모임의 후보 날짜이며, 각 컬럼 헤더에는 요일(예: "목")과 월·일(예: "04.16")을 2단으로 표시해야 한다
- **FR-003**: 그리드의 세로축(행)은 9시부터 21시까지 30분 단위 슬롯이며, 좌측 시간 라벨 컬럼에는 정시(9, 10, 11, …)만 표시한다 (30분 슬롯 구분은 셀 내부 점선)
- **FR-004**: 각 셀은 한 (날짜, 30분 슬롯) 단위의 가능 인원수에 해당한다

#### 히트맵 농도 규칙

- **FR-005**: 시스템은 모임의 모든 (날짜, 30분 슬롯) 셀 중 **0명이 아닌 셀에 한해** 가능 인원수 기준 내림차순 순위를 매기고, 1~5위에 다음 농도를 적용해야 한다 — 1위: 100%, 2위: 70%, 3위: 50%, 4위: 30%, 5위: 10%
- **FR-006**: 동률 처리 — 동일한 가능 인원수를 가진 셀들은 모두 같은 순위·동일 농도로 묶어 표시하며, 컷오프(5위)에서 동률이 발생해도 잘라내지 않는다
- **FR-007**: 6위 이하 또는 가능 인원수 0명 셀은 베이스 톤(채색 없음/저강도 단일 톤)으로 표시한다
- **FR-008**: 30분 슬롯 셀의 색상은 해당 30분 슬롯의 가능 인원수만으로 결정되며, 같은 시간대(예: 10시 정각 슬롯과 10시 30분 슬롯)는 서로 독립적으로 색상이 결정될 수 있어야 한다

#### 헤더 영역

- **FR-009**: 헤더 중앙에 "{hostName}님이 초대한 {title}" 형식의 모임 타이틀이 표시되어야 한다
- **FR-010**: 헤더 좌측의 캘린더+ 아이콘 탭 시 새 모임 생성 진입점으로 이동해야 한다(기존 동작 유지)
- **FR-011**: 헤더 우측의 공유 아이콘 탭 시 기존 모임 공유 동작이 트리거되어야 한다
- **FR-012**: 그리드 상단에 "{N}명이 투표했어요" 카운트가 표시되어야 하며, N은 `hasVoted=true`인 참여자 수이다(0 포함)
- **FR-013**: 카운트 바로 우측에 뷰 전환 토글 스위치가 표시되어야 한다

#### 토글 / 뷰 전환

- **FR-014**: 토글 스위치 탭 시 동일 데이터의 기존 캘린더뷰(VoteResultDataView)로 전환되어야 한다
- **FR-015**: 토글 시 그리드와 캘린더뷰는 동일한 모임 데이터에 기반하며, 페이지 단위로 화면 영역만 교체된다(전체 페이지 리로드 아님)
- **FR-016**: 페이지 진입 기본값은 테이블뷰이며, 페이지를 떠난 뒤 재진입 시에도 테이블뷰가 기본이다

#### 스크롤

- **FR-017**: 후보 날짜가 가로 폭에 모두 들어오지 않을 경우 가로 스크롤이 가능해야 한다 (페이지네이션 아님)
- **FR-018**: 시간 영역이 세로 폭에 모두 들어오지 않을 경우 세로 스크롤이 가능해야 한다
- **FR-019**: 좌측 시간 라벨 컬럼은 가로 스크롤 시 고정되어야 한다
- **FR-020**: 상단 날짜 헤더 행은 세로 스크롤 시 그리드 영역 내에서 적절히 인식 가능하도록 처리되어야 한다 (예: 헤더가 페이지 상단 헤더 바로 아래에 위치해 그리드만 스크롤되거나 sticky 처리)
- **FR-021**: 첫 진입 시 우측 가장자리에 다음 날짜 컬럼이 일부만 보여 추가 컬럼이 있음을 암시해야 한다(스크롤 가능성 시각적 단서)

#### 하단 액션

- **FR-022**: 화면 하단에 "투표 수정하기"(보조)와 "투표하기"(주) 두 버튼이 가로로 나란히 항상 표시되어야 한다 (사용자 투표 여부와 무관)
- **FR-023**: "투표하기"는 `/meet/{meetingId}/register`로, "투표 수정하기"는 `/meet/{meetingId}/edit`로 이동해야 한다
- **FR-024**: 하단 버튼 영역은 그리드 스크롤과 무관하게 페이지 하단에 고정되어야 한다(현재 VoteActionButtons 동작과 동일)

### Key Entities _(include if feature involves data)_

- **Meeting**: 모임. 식별자(id), 제목(title), 호스트명(hostName), 후보 날짜 목록, 참여자 목록 보유.
- **Participant**: 참여자. 이름, 투표 완료 여부(hasVoted), 가능 시간 슬롯 목록(시간 슬롯 데이터 모델은 별도 명세에서 정의).
- **TimeSlot Cell**: 그리드의 단일 셀. (date, 30-min slot) 키와 해당 슬롯에 가능하다고 투표한 참여자 수(`availableCount`)로 구성. 농도 부여를 위한 순위 계산의 기본 단위.
- **HeatmapRanking**: 모임 단위로 모든 0명 초과 셀에 대해 산출되는 가능 인원수 기준 내림차순 순위 + 농도 매핑 결과. 1~5위(동률 포함)는 각각 100/70/50/30/10% 농도, 그 외는 베이스.
- **ViewMode**: `table` | `calendar` 두 값. 기본은 `table`. 페이지 내부 상태로만 보유(URL/세션 보존은 이번 명세에서 결정하지 않음).

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 사용자는 화면 진입 후 3초 이내에 가장 가능 인원이 많은 시간 슬롯(1위)을 시각적으로 식별할 수 있다(농도 차이가 충분히 변별됨).
- **SC-002**: 후보 날짜 10개, 참여자 30명 규모의 모임에서도 그리드 초기 표시까지 1초 이내에 렌더링된다.
- **SC-003**: 가로 스크롤로 후보 날짜 전체를 60fps 수준의 끊김 없는 인터랙션으로 탐색할 수 있다(중저가 모바일 환경 기준).
- **SC-004**: 토글 전환 시 200ms 이내에 다른 뷰로 화면이 교체된다.
- **SC-005**: 투표자 0명 / 일부만 / 전원 / 동률 등 4가지 데이터 시나리오 모두에서 그리드가 깨짐 없이 표시되고 농도 규칙이 일관되게 적용된다.
- **SC-006**: "투표하기"·"투표 수정하기"·공유·새 모임 생성 진입점 4종 모두 한 번의 탭으로 의도한 다음 화면에 도달한다.

## Assumptions

- **시간 슬롯 데이터 모델 가용성**: 30분 단위 가능 시간 슬롯이 참여자별로 조회되는 데이터 소스(API/엔티티)가 존재한다고 가정한다. 해당 데이터 모델·API 확장은 본 명세 범위 외(별도 명세). 초기 구현 시 mock 데이터로 그리드를 검증할 수 있다.
- **시간 범위(9~21시)는 고정**: 모든 모임에서 9시부터 21시까지로 가정한다. 모임별 가변 시간 범위는 본 명세 범위 외.
- **0명 슬롯 처리**: 가능 인원 0명인 슬롯은 순위 산정에서 제외하므로, 모든 슬롯이 0명인 모임에서는 농도 부여가 일어나지 않고 모두 베이스 톤이다.
- **동률 처리 정책**: 동률은 같은 순위·같은 농도로 묶어 표시하며, 컷오프에서 잘라내지 않는다(예: 5위 동률 3개는 모두 10%).
- **토글 상태 보존**: 새로고침/재진입 시 기본은 테이블뷰. URL 쿼리·세션·로컬스토리지로의 상태 보존 여부는 본 명세에서 결정하지 않으며 plan/추후 결정.
- **셀 탭 인터랙션**: 본 명세 범위 외(추후 결정). 현 시점에서는 셀이 탭 가능하지 않거나, 시각적 피드백만 있고 별도 동작이 없을 수 있다.
- **캘린더뷰 데이터 매핑**: 토글 시 표시되는 기존 캘린더뷰(VoteResultDataView)는 현재 그대로 재사용한다. 시간 슬롯 단위 데이터를 날짜 단위 카드로 어떻게 요약·매핑할지는 데이터 모델 확장 명세에서 결정하며, 본 명세는 "기존 컴포넌트가 받던 데이터 형태가 그대로 공급된다" 가정.
- **헤더 동작 재사용**: 좌상단 캘린더+(새 모임 생성)와 우상단 공유는 현재 코드베이스에 이미 존재하는 동작/진입점을 그대로 재사용한다.
- **하단 버튼 동작 재사용**: 현 `VoteActionButtons` 컴포넌트의 동작·표시 정책(둘 다 표시, 각각 register/edit 라우팅, Amplitude 이벤트 발화)을 그대로 따른다.
